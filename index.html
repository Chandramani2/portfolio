EverAI
Senior Software Development Engineer
Remote · Europe
1 year - Present
  • Redis sliding-window rate limiter — fixed broken per-pod counters, cut infra cost 18%. We had per-pod in-memory rate limit counters. With 10 pods, each user effectively got 10× their actual limit — VIP users were uncapped, free-tier users blew through limits. I moved rate limiting to Redis using sorted sets: ZADD the current request timestamp, ZREMRANGEBYSCORE to prune the window, ZCARD to count, all in one pipeline. Three tiers (free: 60/min, premium: 300/min, VIP: 1000/min) from the JWT claim. Fail-open on Redis error so a cache outage never takes down the API. Result: 18% infra cost reduction by eliminating over-provisioning that was compensating for broken limits.
  • S3 presigned URL media system — eliminated the server from the upload hot path, 90% load reduction. Original upload flow: client → API server → S3. For AI-generated images (1–4MB each) at high concurrency, this was saturating our backend connections. Redesigned so clients upload directly to S3 via short-lived presigned URLs. The server only does two things: (1) validates auth and generates the signed URL, (2) listens for S3 event notifications to confirm completion and update the database. The server never touches file bytes. Result: 90% reduction in server upload load, 35% improvement in upload latency.
  • Redis LIST context cache for LLM prompt assembly — eliminated MongoDB roundtrip on every AI request. Every AI request queried MongoDB for the last N conversation messages to build the LLM prompt. For active users chatting every few seconds, this was a database hit on every message. Built a Redis LIST cache (RPUSH new turns, LTRIM to 100 entries, 2-hour TTL). Cache miss → backfill from MongoDB and warm. Also added Redis SETNX job-ID dedup so Kafka redelivery after a pod restart doesn't trigger a duplicate LLM call and double-charge billing. Result: ~1ms context fetch vs ~8ms MongoDB. Zero duplicate LLM calls on crash-recovery.
  • Fixed production WebSocket panic during rolling deploys — race condition on closed channel. Intermittent panics only during deployments. Correlated crash timestamps with deploy events and traced it to the WebSocket Hub's unregister path: a concurrent goroutine was writing to a client.send channel after it had already been closed by unregister. Fixed by ensuring writes to the send channel use a non-blocking select with a default case, and by auditing the close-vs-write ordering across all goroutines. Zero panics since. Also added a test that reproduces the race with go test -race.
  • Prometheus observability for AI pipeline — MTTR reduced 30% by making invisible bottlenecks visible. When I joined, we had uptime monitoring but no AI-specific signals: GPU pod startup time, LLM request queue depth, WebSocket slow-client eviction rate, Kafka consumer lag per partition. I instrumented custom Prometheus histograms for each. Configured AlertManager routing critical events (consumer lag >500, slow client evictions spiking) to Slack with runbook links. Observability became the reason we caught two incidents before users noticed. Result: 30% reduction in mean time to recovery.
  • Docker multi-stage distroless builds — 60% image size reduction, CI from 12min to under 4min. CI builds were taking 12–15 minutes. Root cause: Go module downloads on every run because COPY . . came before go mod download, busting the cache on every code change. Restructured: Stage 1 copies only go.mod/go.sum and runs go mod download (cached until dependencies change). Stage 2 compiles. Stage 3 is distroless/static (~18MB, no shell). Tightened GitHub Actions caching with layer-hash keys. Result: 60% smaller images. CI from 12min → under 4min.
  • pgvector HNSW ANN search — sub-50ms P99 over 10M+ embeddings, 3× faster than naive full-table scan. The memory retrieval component queries the most relevant conversation memories to inject into LLM prompts. Core: pgvector HNSW index on 1536-dim embeddings plus a partial compound B-tree filter on (user_id, persona_id). The B-tree prunes the search to the relevant user's memories before the ANN scan — this filter is what gives the 3× speedup over a naive full-table ANN. Tuned ef_search to 40 (97% Recall@5 at ~6ms query time). Result: sub-50ms P99 ANN search over 10M+ vectors.
